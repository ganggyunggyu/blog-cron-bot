## 2. 핵심 문제 (치명적)

**한 대상이 크롤에서 실패하면 이미 성공한 대상까지 시트 반영과 Dooray가 전부 스킵됐다.**

원인은 `src/cron-distributed-exposure.ts`의 실행 순서였다.

1. `waitForDistributedRun()` 이 작업 스냅샷에서 `failed > 0` 을 보는 즉시 `throw`
2. 그 아래에 있는 대상별 마무리(`runFinalizeStep` 으로 격리된 시트 반영 + Dooray)는 **한 줄도 실행되지 않음**
3. 결과적으로 32분간 크롤한 5개 대상의 결과가 통째로 버려짐

이전에 넣어둔 `runFinalizeStep` 격리 장치는 "마무리 단계에서 터지는 실패"만 막아줬고, 이번처럼 "크롤 단계에서 터지는 실패"는 그 앞에서 전체를 중단시켜 무력화됐다.

### 조치 (적용·배포 완료: `b596120`)

- `waitForDistributedRun` 이 부분 실패를 예외가 아닌 반환값(`DistributedRunOutcome`)으로 넘기도록 변경
  - 모든 작업이 성공/실패로 결판날 때까지 대기 후 결과 반환
  - 중단 요청만 예외로 유지
- 오케스트레이터가 **크롤에 성공한 대상만 골라** 마무리를 끝까지 수행
  - 실패한 대상은 마무리에서 제외 (빈 결과로 시트를 덮어쓰는 사고 방지)
- 외부 IP 중복 검증을 성공 작업만 대상으로 좁힘 (실패 작업은 IP 기록이 없어 오검출됨)
- 크롤 실패 + 마무리 실패를 마지막에 합쳐서 한 번에 보고하고 종료 코드는 실패 유지
- 회귀 테스트 추가: `src/lib/distributed-exposure/run-monitor.test.ts`
  - 한 대상이 실패해도 성공 대상이 마무리 목록에 남는지 고정
  - 시간 초과로 끝나도 성공분이 유지되는지 고정

### 5번 상세 (코드 분석으로 추가 발견)

부분 실패 격리(`b596120`)를 넣은 뒤에도, 외부 IP 유일성 검증이 **마무리 단계 앞**에서 `throw` 하고 있었다. 조건은 네 가지였다.

- 성공 작업에 워커/외부 IP 기록이 없음
- 실행 중 워커의 외부 IP가 바뀜
- 성공 작업 수 ≠ 워커 수 (한 워커가 두 작업을 처리하면 발생)
- 서로 다른 워커가 같은 외부 IP 사용

여기서 터지면 크롤이 전부 성공해도 시트 반영·Dooray가 0건이 되어, 직전 수정이 그대로 무의미해진다. IP 분리는 차단 예방용 위생 점검이지 결과 정합성 조건이 아니므로 **경고로 낮추고 마무리는 그대로 진행**하도록 바꿨다. 경고 내용은 최종 실패 사유에 합쳐 보고된다.

이제 크롤 완료 시점부터 마무리까지 사이에 `throw` 가 하나도 없다.
